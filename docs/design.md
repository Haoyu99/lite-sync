# lite-sync 设计

状态：草案，2026-10-30

全流程的通俗说明见 [flow.md](flow.md)。两者不一致时以本文为准。

## 1. 目标与非目标

目标：

- 在 Windows、macOS、iOS、Ubuntu 上同步同一个 Obsidian 库，包括笔记、附件和 `.obsidian` 配置。
- 准实时：停止编辑约 2 秒后上传，其他设备在几秒内收到。
- 服务器保存全部版本，任何一次写入、删除、恢复都可以撤销。
- 端到端加密：服务器和云厂商只能看到密文。
- 插件端只需要服务器地址、一次性配对码和口令；其余配置在管理后台统一管理。
- 升级插件不要求重建数据库，也不要求所有设备同时升级。
- 单用户：没有账户和用户名的概念。

非目标：

- 逐字的多人协同编辑（OT、CRDT）。
- 块级去重、P2P 同步。
- 兼容 LiveSync 的数据格式。

## 2. 架构

```
┌────────── 每台设备（Win / Mac / iOS / Ubuntu）──────────┐
│ Obsidian 库文件（以它为准）                             │
│ lite-sync 插件：索引 + 待上传队列 + 加解密              │
└──────────────┬──────────────────────────────────────────┘
               │ HTTPS（读写） + WebSocket（变更通知）
┌──────────────▼──────────────────────────────────────────┐
│ 服务器（Docker，反向代理提供 HTTPS）                    │
│  同步 API ── SQLite（设备、文件、版本、配置、审计）     │
│           └─ 密文对象存储（本地磁盘，可选 S3）          │
│  管理后台静态网页（解密在浏览器内完成）                 │
└─────────────────────────────────────────────────────────┘
```

技术选型：

| 部分 | 选择 |
|---|---|
| 共享核心包 `packages/core` | TypeScript：协议类型、加密、合并、配置校验 |
| 插件 `packages/plugin` | TypeScript，只用 Obsidian API 和 `requestUrl`，不用 Node API |
| 服务端 `packages/server` | Node + Hono + SQLite（WAL） |
| 管理后台 `packages/admin` | Svelte + Vite，构建为静态文件，由服务端提供，也可以在本地打开 |
| 部署 | Docker，HTTPS 由已有的反向代理（1Panel）提供 |

## 3. 加密

### 3.1 密钥层级

```
口令 + salt
  │ PBKDF2-SHA256，600,000 次
  ▼
根钥匙（64 字节，只在浏览器或插件内存中）
  ├─ HKDF(info="lite-sync/v1/login") ─> 登录钥匙（32 字节）─> 发给服务器验证
  └─ HKDF(info="lite-sync/v1/kek")   ─> KEK（32 字节，AES-256-GCM）
                                          │ 解开
                                          ▼
                     主密钥 MK（32 字节随机数，初始化时生成，之后不变）
                       ├─ HKDF ─> 内容钥匙（AES-256-GCM，加密文件内容）
                       ├─ HKDF ─> 元数据钥匙（AES-256-GCM，加密路径、修改时间、内容哈希）
                       ├─ HKDF ─> ID 钥匙（HMAC-SHA256，文件 ID = HMAC(规范化路径)）
                       └─ HKDF ─> 配置钥匙（AES-256-GCM，加密统一配置）
```

- 服务器保存：salt、KDF 参数、登录钥匙的 SHA-256、被 KEK 加密的 MK。
- 服务器不保存，也从不接收：口令、根钥匙、KEK、MK 明文。
- 登录钥匙和 KEK 是同一个根钥匙配不同 `info` 分别派生的，从登录钥匙无法推出根钥匙或 KEK。
- 登录钥匙已经过 60 万轮计算，熵足够，服务器端再做一次 SHA-256 即可，不需要第二次慢哈希。
- 修改口令只需要重新加密 MK，不用重新加密数据，已加入的设备也不受影响。
- PBKDF2 是 iOS WebView 的 WebCrypto 原生支持的算法。KDF 参数存在服务器上，以后可以提高迭代次数或改用其他算法，不影响已有数据。

### 3.2 密文格式

```
[格式版本 1 字节][IV 12 字节][密文 + GCM 标签 16 字节]
```

- 每次加密都使用随机 IV。
- AAD 为 `lite-sync/v1|<用途>|<文件 ID>|<rev>`。服务器无法把一个文件的密文换到另一个文件，也无法把旧版本冒充成新的版本号。
- 内容在加密前不压缩，避免通过密文长度推断内容。

### 3.3 服务器能看到什么

| 能看到 | 看不到 |
|---|---|
| 文件数量、每个版本的密文大小 | 文件名、文件夹结构 |
| 写入时间、写入设备、操作类型 | 文件内容、内容哈希 |
| 同一文件 ID 的修改频率 | 统一配置的内容 |
| 设备名、平台、插件版本（明文登记） | 口令、主密钥 |

### 3.4 设备上的密钥

- MK 保存在 Obsidian 的设备本地存储（`app.saveLocalStorage`）中，不写进插件的 `data.json`。`data.json` 会进入 iCloud 备份，也会被 `.obsidian` 同步发到其他设备。
- 设备磁盘的加密由操作系统负责：FileVault、BitLocker、iOS 数据保护、LUKS。
- 吊销设备令牌后，这台设备无法再访问服务器。但它已经拿到的 MK 无法收回。如果设备丢失，应在后台执行"轮换主密钥"（第三阶段）：生成新 MK，在浏览器中用新 MK 重新加密所有当前版本。

### 3.5 口令丢失

口令只用于登录后台和让新设备解开主密钥，插件里没有重设口令的入口。口令丢失时：

- 已加入的设备照常同步，不受影响。
- 后台无法登录，也无法加入新设备。
- 没有找回办法。只能在内容最全的设备上重新初始化服务器并重新上传，历史版本会丢失。

所以口令必须存进 Bitwarden，并另外保留一份纸质备份。

### 3.6 威胁与边界

- 服务器磁盘或备份泄露：攻击者只能离线猜口令，每次猜测需要 60 万轮 PBKDF2。口令使用 Bitwarden 生成的 5 个以上单词的密码短语。
- 只泄露口令：攻击者还需要服务器上被锁住的 MK。它只提供给已登录的后台（需要 TOTP）或持有设备令牌的设备，所以单独的口令不够用。
- 设备令牌泄露：只能下载密文。可以在后台吊销。
- 服务器被完全控制：攻击者可以篡改后台网页的 JavaScript，在你下次登录时截获口令。这是网页端端到端加密都有的限制。对策：怀疑服务器被入侵时，使用本地打开的后台（`npm run admin:local`），它只把服务器当作 API 使用。插件不受影响，因为插件代码在设备本地运行。
- 口令丢失：见第 3.5 节。

## 4. 设备注册

1. 在后台点"添加设备"。服务器生成一次性配对码，10 分钟内有效，只能使用一次。
2. 在插件里填写服务器地址和配对码。插件调用 `POST /v1/pair`，换取长期设备令牌，并登记设备名、平台和插件版本。
3. 插件下载 salt、KDF 参数和被锁住的 MK，要求输入一次口令。插件在本地算出 KEK，解开 MK，存入设备本地存储，然后丢弃口令和根钥匙。口令错误时 GCM 校验失败，提示重新输入。
4. 服务器只保存设备令牌的 SHA-256。

## 5. 管理后台

入口：`https://<你的域名>/admin`。单用户，没有用户名。

### 5.1 首次初始化

服务器首次启动时在日志中打印一次性初始化链接（`docker logs lite-sync`），该链接只能使用一次。打开后，浏览器在本地：

1. 生成 salt，用你输入的口令算出登录钥匙和 KEK。
2. 生成 MK，用 KEK 加密。
3. 上传 salt、KDF 参数、登录钥匙、被锁住的 MK。服务器只保存登录钥匙的 SHA-256。

然后可选地开启双重认证（可以跳过，之后在设置里开启或关闭）：

1. 服务器生成 20 字节 TOTP 密钥，页面在浏览器内生成二维码（`otpauth://totp/lite-sync?secret=…&issuer=lite-sync`）。
2. 用 Google Authenticator 扫码，输入一次验证码确认后才正式启用。
3. 显示 10 个一次性恢复码。服务器只保存它们的哈希。

### 5.2 登录

1. 浏览器调用 `GET /admin/api/prelogin` 取得 salt 和 KDF 参数（无需鉴权，salt 可以公开）。
2. 你输入口令（Bitwarden 自动填充）和 TOTP 验证码。
3. 浏览器在本地算出登录钥匙和 KEK，只把登录钥匙和验证码发给 `POST /admin/api/login`。
4. 服务器比对登录钥匙的 SHA-256，校验 TOTP，通过后建立会话。
5. 浏览器下载被锁住的 MK，用 KEK 在本地解开。MK 只保存在页面内存中，关闭页面或空闲 30 分钟后丢弃。

登录后可以：设备列表、添加或吊销设备、存储用量、同步状态、审计日志、浏览文件、查看历史和差异、恢复版本、整库时间点恢复、编辑统一配置、明文导出。

### 5.3 TOTP 细节

- RFC 6238，SHA-1，6 位，30 秒一格。兼容 Google Authenticator、Microsoft Authenticator、1Password 等。
- 允许前后各一格的时钟误差。服务器需要开启 NTP。
- 同一个时间格的验证码只能使用一次。
- TOTP 密钥用环境变量 `LITE_SYNC_SERVER_KEY` 派生的密钥加密后存入数据库。单独泄露数据库文件不会泄露 TOTP 密钥。
- 实现使用 Node 内置 `crypto`，不依赖第三方 TOTP 库。

### 5.4 安全措施与恢复

- 登录接口限速：连续失败 5 次锁定 15 分钟。
- 会话 Cookie：HttpOnly、Secure、SameSite=Strict。
- 危险操作（清理历史、修改保留策略、整库恢复、批量删除、轮换主密钥、修改口令）要求重新输入口令和验证码。
- 验证码丢失：使用恢复码登录，或在服务器上执行 `docker exec lite-sync reset-2fa`，下次登录时重新绑定。
- 口令丢失：见第 3.5 节。
- TOTP 不放在 Bitwarden 中，避免口令和第二因素集中在同一处。
- Bitwarden 与 lite-sync 部署在同一台服务器上时，Bitwarden 客户端的本地缓存可以在服务器故障时继续提供口令，但缓存可能因退出登录、重装或清空数据而消失。口令和恢复码另外保存一份纸质副本。

## 6. 服务器数据模型

- `vault`（一条）：salt、KDF 参数、登录钥匙的 SHA-256、被锁住的 MK、口令更新时间。
- `admin`（一条）：加密的 TOTP 密钥、上次使用的时间格、恢复码哈希列表、失败计数和锁定时间。
- `sessions`：会话 ID 的哈希、创建时间、最后活动时间。
- `devices`：id、名称、平台、插件版本、令牌哈希、最后在线时间、已确认的 seq、待上传数量、吊销时间。
- `pairing_codes`：配对码哈希、过期时间、是否已使用。
- `files`：文件 ID、当前 rev、是否已删除。
- `versions`（只追加）：文件 ID、rev、全局 seq、对象键、大小、加密元数据、操作类型（写入、删除、恢复）、设备 id、时间、批量操作 id。
- `objects`：密文对象，按密文的 SHA-256 命名，可以被多个版本引用。
- `config_versions`：加密的统一配置，带版本。
- `audit`：管理操作日志。

## 7. API

设备接口（`/v1`，设备令牌鉴权）：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/pair` | 用配对码换取设备令牌（无需令牌） |
| GET | `/v1/vault` | 读取 salt、KDF 参数和被锁住的 MK |
| GET | `/v1/changes?since=<seq>` | 分页获取变更 |
| GET | `/v1/files/<id>` | 下载当前版本 |
| GET | `/v1/files/<id>/versions/<rev>` | 下载历史版本（合并时取祖先） |
| PUT | `/v1/files/<id>` | 上传，请求头 `X-Base-Rev`；基准版本不是最新时返回 409 |
| DELETE | `/v1/files/<id>` | 删除，同样需要 `X-Base-Rev` |
| POST | `/v1/batch` | 原子提交多项操作（重命名、恢复） |
| GET | `/v1/config` | 读取加密的统一配置 |
| POST | `/v1/status` | 上报待上传数量、已同步的 seq |
| WS | `/v1/events` | 推送新的 seq |

管理接口位于 `/admin/api`，使用会话 Cookie 鉴权，与设备接口分开。`prelogin`、`login` 和一次性初始化接口除外。

## 8. 同步流程

### 8.1 设备本地状态

- 索引：路径 → 文件 ID、上次同步的 rev、上次同步的内容哈希、mtime、大小。
- 待上传队列：持久化保存，重启后继续上传。
- 游标：上次处理到的 seq。

索引保存在库外的设备本地存储（IndexedDB）中。索引丢失时，按第 9.4 节的新设备加入规则重建，不会覆盖任何文件。

### 8.2 本地 → 云端

1. 文件事件触发后等待约 2 秒；`.obsidian` 目录每 30 秒扫描一次，因为 Obsidian 不为它发出文件事件。
2. 计算内容哈希。与索引一致则跳过。
3. 加入待上传队列，加密并上传，带上 `X-Base-Rev`。
4. 收到 200：更新索引。收到 409：进入冲突处理（第 9 节）。
5. 网络失败时按指数退避重试，队列不丢失。

### 8.3 云端 → 本地

1. 收到 WebSocket 通知时、启动时、iOS 回到前台时，调用 `GET /v1/changes`。
2. 对每个变更：
   - 本地文件与索引中的哈希一致（没有未上传的修改）：下载、解密、校验哈希，写入文件，更新索引。
   - 本地有未上传的修改：先上传本地版本，得到 409 后进入冲突处理。
   - 文件在编辑器中打开并且最近 5 秒内有输入：延后应用。
3. 全部处理完成后才推进游标。

### 8.4 删除和重命名

- 只有 Obsidian 发出删除事件时才同步删除。
- 扫描时发现索引中的文件不存在：重新下载，不当作删除。这能防止 iCloud 把文件移出本机时误删。
- 重命名 = 在新路径写入 + 删除旧路径，通过 `/v1/batch` 一次提交。

### 8.5 状态显示

状态栏显示 `✓ 已同步`、`↑3 待上传`、`↓ 下载中`、`⚠ 离线`、`⚠ 需处理`。设备通过 `/v1/status` 上报状态，后台据此显示每台设备是否已全部上传。

## 9. 冲突与安全保护

### 9.1 冲突策略

| 情况 | 处理 |
|---|---|
| 只有一边修改 | 采用修改的那边 |
| 两边内容相同 | 视为一致 |
| 两边都修改 Markdown 或纯文本 | 从服务器取上次同步的版本作为祖先，进行三方合并；成功则上传结果 |
| 合并失败，或者是二进制文件 | 原路径保留云端版本；本地版本另存为 `<名称> (冲突 <设备> <MM-DD HH:mm>).<扩展名>` 并上传 |
| 两边都修改 JSON 配置 | 按键合并；同一键冲突时采用云端值，本地版本留在历史中 |
| 一边删除，另一边修改 | 保留修改 |

冲突不弹对话框。后台和插件设置页面列出冲突副本。

### 9.2 回滚

- 版本只追加。回滚是用旧内容生成一个新版本，所以回滚本身也可以撤销。
- 整库时间点恢复：在后台选择一个时间点，只为有差异的文件生成新版本。整个操作记为一次批量操作，可以一键撤销。

### 9.3 防止破坏性操作

- 过期设备无法覆盖较新的内容：每次写入都校验基准版本。
- 大批量变更保护：一次同步中要删除或覆盖超过 `massChangeGuard`（默认 20）个文件时暂停，等待确认。
- 没有"重建远程数据库"这种操作。

### 9.4 新设备加入或索引丢失

逐个比较本地文件与云端当前版本：

- 哈希相同：直接关联。
- 只存在于本地：上传。
- 只存在于云端：下载。
- 两边不同：按第 9.1 节处理，不会覆盖任何文件。

### 9.5 历史保留

默认保留 30 天内的全部版本，之后每天保留一个版本，可以在后台调整。被删除的文件至少保留 90 天。

## 10. `.obsidian` 同步

- 同步：`appearance.json`、`themes/`、`snippets/`、`hotkeys.json`、`core-plugins.json`、`community-plugins.json`、`plugins/*/{main.js,manifest.json,styles.css,data.json}`，以及其他核心插件的配置文件。
- 始终排除：`workspace.json`、`workspace-mobile.json`、`plugins/lite-sync/`、`plugins/obsidian-livesync/`。
- 插件代码变化后，提示重新加载 Obsidian。
- 可以按平台覆盖配置，比如手机端不同步快捷键。

## 11. 统一配置

插件本地只保存服务器地址、设备令牌、设备名（`data.json` 中）以及 MK（设备本地存储中）。其余配置来自云端，插件缓存最后一次获取的配置，离线时照常工作。

```jsonc
{
  "schema": 1,
  "sync": { "debounceMs": 2000, "configScanSeconds": 30, "maxFileSizeMB": 50, "massChangeGuard": 20 },
  "exclude": [],
  "obsidian": {
    "appearance": true, "themes": true, "snippets": true, "hotkeys": true,
    "corePlugins": true, "communityPlugins": true, "pluginData": true,
    "excludePlugins": ["obsidian-livesync"]
  },
  "overrides": { "mobile": { "obsidian": { "hotkeys": false } } },
  "history": { "keepAllDays": 30, "thenDaily": true, "keepDeletedDays": 90 }
}
```

## 12. 兼容与升级

- 三处版本号从第一天固定：密文格式字节、API 路径 `/v1`、配置 `schema`。
- 新客户端必须能读取所有旧格式。服务器继续支持旧客户端。
- 客户端遇到不认识的格式时，跳过对应文件并报告，不删除也不覆盖任何内容。
- 服务器可以声明最低客户端版本。低于该版本的客户端进入只读模式并提示更新。
- 设备之间唯一需要一致的是主密钥。

## 13. 安装与更新

- 构建产物发布到 GitHub Release，每台设备通过 BRAT 安装，手动更新。
- 源码仓库可以放在 GitLab，GitHub 只用于发布。

## 14. 分阶段实现

1. 替换 LiveSync：服务端核心、加密、单口令登录 + TOTP + 恢复码、设备配对、笔记实时同步、版本历史、大批量变更保护、最简后台（初始化、登录、设备列表、添加和吊销设备）。
2. 后台完善：文件浏览、历史和差异、恢复版本、整库时间点恢复、统一配置编辑。
3. `.obsidian` 同步、按平台覆盖、主密钥轮换。
4. 运维：历史清理、自动备份、明文导出、通行密钥（Touch ID、面容 ID）登录。

## 15. 从 LiveSync 迁移

1. 在所有设备上停用 LiveSync，并备份一份库。
2. 在内容最全的设备上配对，完成首次上传。
3. 其他设备逐台配对，按第 9.4 节加入。
4. 检查后台中的冲突副本，确认后删除 LiveSync 插件。
